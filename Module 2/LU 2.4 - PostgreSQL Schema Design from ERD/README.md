# Helpdesk Schema Repair

The initial PostgreSQL migration implements the Helpdesk ER diagram. The project provides 36 pgTAP assertions for schema validation.

## ERD-to-Schema Decisions

### Decision 1: UUID Primary and Foreign Keys
ERD said: Entity identifiers and relationships use UUIDs.
Schema decided: Every table has a UUID primary key generated by `gen_random_uuid()`, and every foreign key is UUID.
Reason: UUIDs keep references type-consistent across the schema and give each row a generated identifier without integer sequences.

### Decision 2: ON DELETE Behaviour
ERD said: Each relationship specifies how dependent records behave when their referenced row is deleted.
Schema decided: Organization references from agents and tickets and required agent references from ticket creators, comment authors, and tag assigners use `RESTRICT`; ticket references from comments/ticket_tags and tag references from ticket_tags use `CASCADE`; a ticket's optional assignee uses `SET NULL`; a tag's organization reference uses `CASCADE`.
Reason: Restriction protects referenced agents and organizations where specified, cascades remove dependent comments and ticket-tag links, deleting an organization removes its tags, and deleting an assignee preserves the ticket while clearing that optional relationship.

### Decision 3: Default Values and Constraints
ERD said: Plans, roles, priorities, and statuses are limited to specified values; creation timestamps and selected fields have defaults.
Schema decided: Those fields use `TEXT` with `CHECK` constraints; ticket status defaults to `open`; creation timestamps default to `NOW()` as `TIMESTAMPTZ`; comment `internal` defaults to `FALSE`; required fields are `NOT NULL` and optional fields remain nullable.
Reason: Checks enforce the allowed values without introducing enum types, and defaults consistently initialize values while preserving the ERD's nullable fields.

## Rejected Table Shape

### Shape: Tags Array Inside Tickets
What it was: A `tags TEXT[]` column on `tickets` stored multiple tag names in one field.
Why rejected: Tickets and tags have a many-to-many relationship, so the schema uses a separate `tags` entity and `ticket_tags` join table, with one row per ticket-tag association.
What would break: An array cannot enforce a foreign key for each tag or carry association data such as `added_by` and `added_at`; it also makes tag updates, validation, and relational queries less reliable.

## Validation

Requirements: Node.js/npm, PostgreSQL, and pgTAP (`pg_prove`).

Run `npm run db:reset` to drop and recreate `helpdesk_test` and apply the migration, then run `npm test` to execute the 36 pgTAP assertions.
